Piano Snakes & Ladders — Implementation Plan

Per-Account Studio Config

One shared page, one repo. Each studio gets a directory with their branding and (optionally) their own question bank. You create it, push it, hand them a link — no codes, no accounts, no in-browser editor.

✦Context

Why this, and what "done" looks like

Goal

Sell this game to other piano studios as a one-time payment, hosted entirely on your existing GitHub Pages site — no per-studio hosting.

Current state

One public page with branding and a 30-question Thai bank hardcoded into the JS. Rebranding means hand-editing the file.

Desired behavior

The same one page. Each studio's link includes their account slug; the page loads that account's branding + questions from the repo.

Who edits what

You create and edit each account's files in the repo. Studios never touch code — they just open their link.

↳
This replaces the earlier "unlock code + studios self-edit in their browser" direction. That design solved a problem you don't actually have — you already said you want to build studios' custom questions for them, not hand them an editor. Owner-managed per-account files are simpler to build and match how you actually plan to work.

1Per-account files in the repo

Every studio is a directory; every directory is one JSON file
accounts/harmony-music/config.json

Shape mirrors the existing config objects exactly, so nothing new has to be invented:

FieldMeaning
studio.nameShown above the title and in the browser tab — same shape as the existing STUDIO object.
studio.linkOptional; empty string renders the name as plain text.
questionsOptional. Omit it entirely and the studio gets your standard 30-question bank by default. Include a full array (same shape as QUESTION_BANK: {q, options[4], correct, visual?}) only for studios who paid for custom content.

Onboarding a new studio

  1. Get paid.
  2. Create accounts/<slug>/config.json — copy the template, fill in their name/link. Add a questions array only if they bought custom content.
  3. Commit, push to main — GitHub Pages redeploys in about a minute, same as every change so far this project.
  4. Send them their link: sping128.github.io/piano-snakes-and-ladders/?studio=<slug>

Optional convenience: tools/scaffold-account.js <slug> "Studio Name" "https://link" generates the file from a template instead of hand-writing JSON — a nice-to-have, not required for v1.

✓
Bonus this design gets you for free: access is revocable. Delete or rename an account's folder and their link quietly falls back to the default demo — something the unlock-code approach explicitly couldn't do.

2How a page picks its account

URL parameter → fetch → validate → override, or fall back to the default demo
flowchart TD
  A["Studio opens their link\n?studio=<slug>"] --> B{"studio param\npresent & safe?"}
  B -- No --> C["Boot with default demo\n(your branding + built-in 30 questions)"]
  B -- Yes --> D["fetch accounts/<slug>/config.json"]
  D --> E{"Fetch OK &\nvalid shape?"}
  E -- No --> C
  E -- Yes --> F{"Config includes\ncustom questions?"}
  F -- No --> G["Apply their branding\n+ default 30-question bank"]
  F -- Yes --> H["Apply their branding\n+ their custom question bank"]
  G --> I["Rest of app boots:\nboard, setup screen, etc."]
  H --> I
  C --> I

Slug safety

The slug drives a fetch path, so it must be restricted before use — e.g. /^[a-z0-9-]+$/ — to rule out path traversal like ?studio=../../secrets. Anything that doesn't match falls back to the default demo, same as a missing param.

Boot order becomes async

Today's boot runs synchronously top-to-bottom. Loading a config now means a fetch(), so the existing init (build the preview board, wire up buttons, restoreSavedGame(), etc.) needs to await the account lookup first. Same-origin JSON fetches are fast, but to avoid a flash of default branding before the real one applies, keep the page shell hidden (a simple opacity fade) until the lookup resolves.

3Runtime integration

Same override mechanism as before, different trigger

STUDIO and QUESTION_BANK change from const to let — every existing call site reads them live by identifier, so reassignment is safe.

A new async loadAccountOverride() runs at boot: reads ?studio= from the URL, validates the slug, fetches the config, validates its shape with the same all-or-nothing validateStudioConfig() style already used for the existing game-save restore, and reassigns STUDIO/QUESTION_BANK only on success. Any failure — no param, bad slug, 404, malformed JSON — falls through to today's hardcoded defaults untouched.

GitHub Pages on the free tier requires the repo to stay public. That means accounts/ — every customer's directory name, and any custom question content you write for them — is browsable by anyone on GitHub, not just people with the direct link. Three ways to handle it:

Accept it

Do nothing extra. For a niche classroom tool, the realistic odds of a competitor studio browsing your repo tree are low.

Simplest

Go private

Make the repo private. GitHub Pages from a private repo needs a paid personal plan — or switch to Cloudflare Pages/Netlify, both free and both support private-repo deploys.

Most private, more setup

Opaque slugs

Use a random slug instead of the studio's name as the directory (e.g. a83f2c instead of harmony-music). Hides identity in the URL/repo tree, but anyone browsing accounts/ can still open any folder and read its content.

Partial, no extra cost

▶Verification plan

No test framework exists — verified the same way every change has been verified so far: a headless Playwright script against the real rendered page
  1. No ?studio= param → default branding + built-in 30 questions, unchanged from today.
  2. Unsafe slug (e.g. ../x) → falls back to default, no fetch attempted outside accounts/.
  3. Valid slug, account has branding only (no questions) → branding overridden, question bank still the default 30.
  4. Valid slug, account has custom questions → branding and questions overridden; play to a ladder/snake and confirm the quiz pulls from the custom bank, not the default — proves game logic reads the override, not just a preview panel.
  5. Nonexistent slug (valid format, no matching folder) → fetch 404s → falls back to default demo, no error shown to the visitor.
  6. Malformed config.json (e.g. a question missing an option) → rejected by validateStudioConfig(), falls back to default rather than half-applying.
  7. Full regression: play a complete game to a win on an account with custom questions — reset-confirm, save/resume, and win-flow all still work unchanged.
